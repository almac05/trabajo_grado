Sección 1: Estrategia de Gestión y Ciclo Sprints (Scrum-ML)

El proyecto adopta una variante de Scrum adaptada a proyectos de Machine Learning (Scrum-ML), en la que cada sprint de dos semanas produce un incremento verificable: desde un dataset limpio hasta un experimento registrado en MLflow. Antes de los sprints de modelado se ejecutan spikes de viabilidad cortos que reducen el riesgo de invertir semanas en un camino técnico inviable.

1.1 Identificación de Spikes

Un spike es una tarea exploratoria de investigación acotada en tiempo (1 a 3 días) cuyo objetivo es resolver una incertidumbre técnica crítica antes de comprometer el equipo con un plan de implementación. Para este proyecto se identifican tres spikes previos al modelado:

Spike S-01: Auditoría de Completitud y Calidad del Dataset APC/GPS (2 días)

Objetivo: Verificar que los registros de conteo APC y telemetría GPS en la base de datos bd_montebello_rdw (Registel MySQL) cubren el período 2022–2025 con suficiente densidad temporal para entrenar modelos de series de tiempo en Ruta 1 y Ruta 3.

Actividades concretas:

  • Ejecutar consultas SQL de conteo de registros por mes × ruta × fuente (APC, GPS, despacho).
  • Calcular porcentaje de nulos por columna clave (PASAJEROS, LATITUD, HORA_INICIAL_REAL).
  • Identificar gaps temporales consecutivos mayores a 30 minutos y su distribución mensual.
  • Comparar cobertura entre Ruta 1 y Ruta 3 para anticipar tratamientos diferenciados.

Criterio de salida (Done): Reporte de cobertura con ≥ 85% de registros válidos por mes-ruta; listado explícito de los períodos con datos insuficientes y la estrategia de imputación acordada (forward-fill ≤ 2 h; exclusión si el gap supera 4 h continuadas).

Riesgo mitigado: Evitar iniciar el feature engineering y el entrenamiento de modelos LSTM/ARIMA sobre ventanas con gaps que invalidan la autocorrelación temporal y generan data leakage.

Spike S-02: Validación del Baseline Naive y Umbral de Predictibilidad (1 día)

Objetivo: Establecer un floor de métricas con un predictor naive (promedio histórico por franja horaria y día de semana) sobre el conjunto de test holdout, antes de entrenar modelos complejos.

Actividades concretas:

  • Implementar NaiveMeanPredictor: para cada franja horaria de 30 min × día de semana, usar la media histórica del mismo período en los años anteriores.
  • Calcular MAE, RMSE y MAPE sobre los últimos 3 meses de datos (conjunto de test).
  • Registrar el experimento en MLflow bajo el tag experiment_phase=spike.

Criterio de salida: Métricas del baseline documentadas en MLflow; confirmación de que el MAPE naive < 40% (señal temporal predecible). Si MAPE naive ≥ 40%, se revisará la granularidad de la variable objetivo antes de continuar.

Riesgo mitigado: Si la señal no es predecible ni con el estimador más simple, no tiene sentido invertir 4 semanas en LSTM. El spike genera la evidencia para tomar esa decisión el día 3 del proyecto, no el mes 4.

Spike S-03: Factibilidad de Integración de Variables Climáticas (1 día)

Objetivo: Determinar si los datos de precipitación para Cali (fuente: IDEAM o API meteorológica abierta) son integrables temporalmente con los registros de Montebello y si correlacionan estadísticamente con el conteo de pasajeros.

Actividades concretas:

  • Descargar datos históricos de precipitación diaria/horaria para Cali 2022–2025 (estación IDEAM más cercana o API Open-Meteo).
  • Calcular correlación de Spearman entre lluvia (mm/h) y conteo APC por franja horaria.
  • Evaluar cobertura temporal: ¿existen huecos que coincidan con los huecos del dataset principal?

Criterio de salida: Correlación significativa en al menos una franja horaria (|ρ| > 0.15, p < 0.05). Si la correlación no es significativa, se excluye la variable climática y se usa únicamente una variable binaria is_rainy_season derivada del calendario.

Riesgo mitigado: Evitar añadir complejidad de integración (API externa, gaps adicionales) si la variable climática no aporta señal estadística real en este contexto operativo.

Arquitectura multi-stage del Dockerfile

El Dockerfile actual del proyecto implementa un patrón multi-stage que separa el entorno de compilación del entorno de ejecución, reduciendo el tamaño de la imagen final en aproximadamente un 60%: 

# Stage 1: Builder — compila wheels nativos (gcc, g++, libmysqlclient-dev)
FROM python:3.11-slim AS builder
RUN apt-get install -y build-essential gcc g++ default-libmysqlclient-dev ...
WORKDIR /app
COPY pyproject.toml README.md ./
COPY src/ ./src/
RUN pip install --prefix=/install .   # instala el paquete + todas sus dependencias

# Stage 2: Runtime — imagen mínima, sin herramientas de compilación
FROM python:3.11-slim AS runtime
RUN apt-get install -y libgomp1 default-libmysqlclient-dev  # solo runtime libs
COPY --from=builder /install /usr/local     # copia wheels compilados
COPY --chown=app:app src/ ./src/
ENV PYTHONPATH=/app/src
USER app   # principio de menor privilegio
CMD ["python", "-m", "proyecto_grado.etl.pipeline"]

3.2 Estrategia de Pruebas con pytest (Patrón AAA)

Las pruebas unitarias se enfocan en las funciones críticas de soporte que rodean el modelo: preprocesamiento, ETL, feature engineering, construcción de secuencias y el módulo heurístico de despacho. El modelo en sí se verifica a través de sus criterios de aceptación cuantitativos (§1.2), no a través de pruebas unitarias. Todas las pruebas siguen el patrón AAA (Arrange–Act–Assert).

El proyecto ya cuenta con 478 LOC de pruebas unitarias en 7 archivos para el pipeline ETL (tests/unit/). Los siguientes tests amplían la cobertura hacia los módulos de features, modelos y dispatch.

Test existente representativo: test_transforms.py

# Prueba existente — patrón AAA aplicado al ETL
def test_combinar_fecha_hora_crea_datetime_y_marca_invalidos():
    # Arrange
    df = pd.DataFrame({
        "FECHA": ["2024-04-16", "2024-04-16", "bad-date"],
        "HORA":  ["08:30:00",  "sin hora",   "09:15:00"],
    })
    # Act
    result = transforms.combinar_fecha_hora(df, "FECHA", "HORA", "FECHA_HORA")
    # Assert
    assert result.loc[0, "FECHA_HORA"] == pd.Timestamp("2024-04-16 08:30:00")
    assert pd.isna(result.loc[1, "FECHA_HORA"])   # hora inválida → NaT
    assert pd.isna(result.loc[2, "FECHA_HORA"])   # fecha inválida → NaT

def test_validate_passenger_counts_rechaza_negativos_y_sobre_capacidad():
    # Arrange
    df = pd.DataFrame({
        "PASAJEROS": [15, -3, 0, 42, 200, -1],

    })
    MAX_CAPACITY = 80

    # Act
    result = validate_passenger_counts(df, max_capacity=MAX_CAPACITY)

    # Assert
    assert result["is_valid"].sum() == 3      # 15, 0, 42 son válidos
    assert not result.loc[1, "is_valid"]      # -3 es inválido
    assert not result.loc[4, "is_valid"]      # 200 > 80, sobre capacidad
    assert result.loc[2, "is_valid"]          # 0 pasajeros es válido (bus vacío)

def test_build_sequences_genera_dimensiones_correctas():
    # Arrange
    n_obs    = 100
    seq_len  = 24      # 12 horas de contexto (franjas de 30 min)
    horizon  = 3       # predicción a 90 minutos
    series   = np.arange(n_obs, dtype=float)

    # Act
    X, y = build_sequences(series, seq_len, horizon)

    # Assert
    expected_samples = n_obs - seq_len - horizon + 1   # = 73
    assert X.shape == (expected_samples, seq_len)
    assert y.shape == (expected_samples, horizon)
    assert X[0, -1] == float(seq_len - 1)   # último valor de la 1ª secuencia
    assert y[0,  0] == float(seq_len)        # primer valor objetivo

def test_mape_excluye_ceros_en_denominador():
    # Arrange
    y_true = np.array([10.0, 0.0, 20.0, 15.0])
    y_pred = np.array([9.0,  1.0, 18.0, 16.0])

    # Act
    mape = calculate_mape(y_true, y_pred)

    # Assert: solo calcula sobre [10, 20, 15] — excluye el cero
    expected = np.mean([abs(10-9)/10, abs(20-18)/20, abs(15-16)/15]) * 100
    assert abs(mape - expected) < 0.001
    assert not np.isnan(mape)    # nunca debe devolver NaN

4.2 Análisis de Ruta Crítica (Critical Path Method — CPM)

La ruta crítica es la secuencia de actividades encadenadas sin holgura cuya demora retrasaría la fecha de entrega final. Se identificó aplicando el método CPM sobre el grafo de dependencias del WBS. La duración total de la ruta crítica es de 22 semanas (ajustada al calendario con paralelización de actividades independientes).

Ruta crítica identificada

S-01: Auditoría datos
   → EDA Ruta 1 + EDA Ruta 3 (paralelo)
   → Diccionario de features (depende del EDA)
   → Feature engineering temporal + operativo (paralelo)
   → Pipeline features → Parquet ML-ready
   → Train/val/test splits walk-forward
   → Entrenamiento XGBoost + tuning [cuello de botella 1]
   → Entrenamiento LSTM/GRU [cuello de botella 2]
   → Evaluación comparativa y selección del modelo ganador
   → Módulo heurístico de despacho
   → Pruebas de integración end-to-end
   → Redacción metodología + resultados
   → Revisión Dra. Maritza Correa [cuello de botella 3]
   → Correcciones y entrega final

Tabla 7. Análisis de cuellos de botella y estrategias de mitigación

# Cuello de botella Impacto si ocurre Holgura Plan de mitigación
1 Datos APC/GPS con calidad insuficiente
(gaps > 4h en períodos extensos, nulos > 15%)		 Bloquea todo el pipeline; modelos entrenados en datos malos son inútiles 0 días Spike S-01 en los primeros 2 días del proyecto. Estrategia de imputación predefinida: forward-fill ≤ 2h; exclusión de registros con gaps > 4h continuas. Si la cobertura de una ruta es < 70%, esa ruta se modela independientemente con menor horizonte temporal.
2 Entrenamiento LSTM/GRU computacionalmente costoso
(tiempo de entrenamiento > 6 h en CPU local)		 Retrasa la fase Alfa en 1–2 semanas; bloquea la comparativa final DL vs ML 0 días Entrenamiento delegado a AWS SageMaker (spot instances ml.p3.2xlarge). Mientras tanto, validar arquitecturas pequeñas (hidden=32, seq_len=12) en CPU local para confirmar que el código es correcto antes de lanzar el job de 8 horas.
3 Disponibilidad de la directora para revisiones
(calendario académico UAO, otros compromisos)		 Puede retrasar la entrega final 1–3 semanas si solo se revisa al final 0 días Programar hitos de revisión parcial en cada fase: revisión 1 al cierre del MVP (15 Aug), revisión 2 al cierre del Alfa (12 Sep), revisión final al cierre del Beta (10 Oct). No acumular toda la revisión en la fase Release.
4 Modelo DL no supera el umbral MAPE ≤ 15%
(señal insuficiente, datos limitados para DL)		 La historia de usuario HU-ML-01 no se puede cerrar con el modelo DL 2 semanas Criterio de fall-back documentado: si el mejor modelo DL (LSTM/GRU) no supera a XGBoost en al menos 2 puntos porcentuales de MAPE, XGBoost se adopta como modelo de producción. El trabajo de grado documenta el análisis comparativo completo como contribución metodológica.
5 Integración de datos climáticos IDEAM con baja disponibilidad Feature engineering climático no disponible; impacta la riqueza del modelo 1 semana Spike S-03 decide en el día 4. Alternativa predefinida: variable binaria is_rainy_season basada en el calendario histórico de lluvias de Cali (bimestres octubre–noviembre y marzo–abril), sin necesidad de API externa.
